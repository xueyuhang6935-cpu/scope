# 知识库现状问题与改进建议

整理日期：2026-10-14（北京时间）。

本文依据当前代码检查和隔离数据库复现，记录知识库的主要问题、实施边界和验收条件。改进建议尚未实施；性能和真实模型回答质量未在本次检查中验证。本文更新只涉及文档，不改变业务代码或项目正式任务的验收状态。

源码链接使用普通相对文件路径，函数名与参考行号写在正文中；行号以本次检查时的代码为准，后续应优先按函数名定位。

## 1. 总体判断

当前知识库已经能满足 Demo 的调查成果留存、证据追溯和对话引用，但查找、复用和故障隔离仍比较薄弱。

当前运作方式为：

```text
调查保存报告和证据
    → 知识库建立成果索引
    → 用户搜索、阅读成果
    → 用户引用到新对话
    → 助手结合历史报告和证据回答
```

知识库目前采用结构化成果索引和原始报告读取。搜索采用字符串匹配，尚未实现报告全文搜索、语义搜索或聊天内自动检索历史成果。

## 2. 主要问题

### 2.1 一份异常成果会让整个知识库列表打不开

**问题：** 列表逐份读取并校验报告，只跳过无权限和不存在的记录。遇到内容校验失败时，会直接返回错误，导致其他有效成果也无法通过列表访问。

**已复现的结果：** 在隔离测试数据库中建立两份成果，将其中一份成果的索引指纹改为异常值：

| 请求 | 实际 HTTP 状态 |
| --- | --- |
| 另一份有效成果的详情 | 200 |
| 整个知识库列表 | 409 |
| 搜索一个没有匹配结果的词 | 409 |

这说明异常发生在筛选之前，单份成果的问题会影响整个列表和搜索入口。本次复现使用现有测试夹具和临时数据库，没有修改正式业务数据库。

**性质：** 已复现的故障隔离缺陷。复现使用主动注入的异常索引指纹，证明的是异常出现后的影响范围，不代表正式数据库已经发生该问题。

**建议：** 保留有效成果的展示，对当前已授权的异常条目单独标记并提供核查信息。详情和引用继续执行完整校验，不允许异常内容绕过校验进入模型上下文。实施时同时检查 `refresh_index()` 和列表读取两个阶段，不能只修改列表的异常分支。无权限成果不展示标题、编号或异常详情；不能用捕获所有异常并静默忽略的方式掩盖系统故障。

**验收条件：** 注入单份指纹异常后，有效成果的列表、搜索和详情正常返回；异常成果不能下载或引用；当前无权限的成果不出现在结果、摘要及计数中；异常有可核查记录。

**代码依据：** [logistics_knowledge.py](../backend/logistics_knowledge.py)，`refresh_index()`（约第 35 行）、`routes()` 内的 `listing()`（约第 137 行）。可执行复现见第 5 节。

### 2.2 搜索容易漏掉用户真正需要的内容

**问题：** 当前只匹配标题、参考时点，以及确定性报告中的重点任务编号。报告结论、限制、未解决事项均未纳入搜索，也没有关键词相关性排序。

**影响：** 如果报告正文提到“时间窗口缺失”，但标题没有这个词，用户搜索该词就可能找不到对应成果。任务编号搜索也不能覆盖所有证据中的任务。

**性质：** 已确认的检索覆盖限制；全文搜索和相关性排序属于能力扩展。

**建议：** 优先补齐报告全文关键词搜索，将结论、限制和未解决事项纳入检索范围，并提供命中摘要。先明确首版搜索字段；“报告全文”不默认包含所有原始证据与处理记录。任务编号检索覆盖范围应单独说明。根据实际使用效果，再决定是否需要语义检索。

**验收条件：** 标题未包含、正文包含的关键词能够命中，并展示来自对应原报告的片段；支持现有区域、状态、时点筛选及稳定分页；无权限成果不参与命中摘要和结果计数；搜索不创建调查、不执行取证工具。

**代码依据：** [logistics_knowledge.py](../backend/logistics_knowledge.py)，`listing()` 中 `terms` 与 `search.strip()` 匹配逻辑（约第 161 行）。

### 2.3 助手复用知识的过程比较费操作

**问题：** 用户必须先去知识库找到报告，再引用到新对话。聊天中提出“以前有没有类似情况”时，助手目前没有自动查找历史成果的能力；前端也没有把成果加入当前对话的入口。

**影响：** 用户正在讨论问题时，需要离开聊天、手动查找资料，再创建另一段对话，原讨论容易被割裂。

**现有能力：** 后端已经通过 `POST /api/logistics/conversations/{identifier}/references` 支持向指定的本人会话添加成果引用，并执行权限、版本、重复引用和消息处理中状态校验。当前缺少的是前端向已有对话引用的入口与会话选择交互，不需要另建一套后端引用能力。

**性质：** 前端能力扩展；聊天内历史成果检索是后续独立能力。

**建议：** 复用现有接口支持引用到当前或选定的本人对话，再提供聊天内历史成果检索。检索结果明确展示来源、原参考时点、区域和成果状态。首版先展示候选供用户选择引用，自动选择资料的行为另行验证。

**验收条件：** 向已有对话引用不新建对话或调查；重复引用不重复添加；版本冲突、消息处理中、非本人会话和成果撤权按后端契约拒绝；取消选择不写入引用。聊天内检索只返回当前授权成果，并且不自动发起调查。

**代码依据：** [KnowledgeDetail.tsx](../src/logistics/KnowledgeDetail.tsx)，`cite()`（约第 22 行）；[logistics_chat.py](../backend/logistics_chat.py)，`reference()`（约第 209 行）。

### 2.4 引用内容没有按当前问题选择

**问题：** 每次提问都会携带已引用成果；每份成果的证据按固定顺序取前 20 个，再进行压缩，没有依据当前问题选择最相关的证据。整体上下文超过 48,000 字节时直接拒绝处理，目前也没有移除引用的入口。

**实际压缩行为：** `compact_evidence()` 会跳过 `source_type='snapshot_task'` 的单任务证据；工具结果中的 `rows` 最多保留前三行，并附带截断说明。历史引用路径没有传入用于人员聚焦的 `scope`，因此不能依靠该压缩函数自动选择问题所指人员。引用的 `model_report` 则直接进入上下文，未按问题选取其中的相关结论。

**影响：** 无关内容可能占用上下文，真正相关的证据可能没有进入模型。引用内容较多或报告较大时，可能触发上下文限额，用户却缺少清理引用的操作。

完整报告保存了证据，不代表模型在本轮回答时已经看到对应明细。例如，用户追问工具结果第四行的特定任务时，前三行压缩视图可能不足以支持回答。48,000 字节限制针对整个序列化上下文，并非仅针对引用，也不是 Token 数限制。

**性质：** 已确认的内容选择与引用管理限制；对实际回答质量的影响尚未通过真实模型验证。

**建议：** 提供查看和移除引用的功能，根据当前问题选择相关报告片段与证据。特定任务或人员追问应读取其原保存证据，避免重新调查。接近上下文限额时，优先减少无关内容，同时保留来源、时点、限制和必要的反证，并说明截断范围；仍无法容纳时提供可执行的缩小范围提示。

**验收条件：** 追问前三行之外的指定任务时，授权明细能够进入模型上下文或明确提示未读取；模型引用只能指向本轮可用且已校验的证据；移除引用后不再进入后续模型上下文，不改写原报告或已保存消息；重复移除幂等，版本冲突和处理中状态得到处理；对整体上下文限额前后的边界进行确定性检查。

**代码依据：** [logistics_chat.py](../backend/logistics_chat.py)，`inputs()` 的历史引用组装（约第 430 行）；[logistics_model.py](../backend/logistics_model.py)，`compact_evidence()`（约第 30 行）；[project/context/logistics_chat.py](../project/context/logistics_chat.py)，`build_messages()` 的 UTF-8 字节限额（约第 28 行）。

### 2.5 列表读取成本偏高，分页没有减少后端工作量

**问题：** 每次搜索或翻页都会扫描符合状态条件的调查、补建索引，再读取全部已索引成果、校验证据和读取处理状态，最后才筛选和分页。这些操作还会占用共享数据库锁。

**影响：** 数据量增加后，知识库读取可能拖慢聊天和调查。当前每页显示 20 条，但后端仍需处理全部成果。

**验证边界：** 这是根据代码确认的性能风险，本次没有做容量压测，不能据此判断当前实际延迟。

**性质：** 待测量的性能风险；是否实施索引优化由测量结果决定。

**建议：** 先在隔离数据库中测量列表、搜索、翻页的耗时、数据库读取次数和锁占用，再决定优化范围。确需保存列表摘要时，在当前授权范围内筛选、排序和分页，详情及引用继续执行完整内容校验。

**摘要一致性约束：** 摘要必须关联原报告的版本或内容指纹，并记录生成规则版本和有效状态。源报告变化或校验异常时，旧摘要不得继续作为有效检索内容；不能通过自动更新归档指纹将异常源内容重新标记为可信。摘要来源的指纹和状态应在读取时核对，耗时的完整证据验证如何移出列表路径，需要单独设计并验证，不能直接省略。

索引保存不等于授权：每次读取仍按当前权限裁定。撤权后不能继续返回相关命中、摘要或计数；多区域成果必须满足原成果的整体范围授权，不能因用户能访问其中一个区域就展示整份成果。摘要失效或重建时，列表应说明当前可检索范围，而非将旧摘要作为正常结果展示。

**验收条件：** 相同授权与筛选条件下，优化前后有效结果、排序和分页一致；源内容变化或异常后旧摘要失效，详情及引用仍拒绝不一致内容；撤权后结果、摘要和计数同步受限；记录相同数据规模下优化前后的耗时与数据库读取次数。具体性能目标在基线测量后确定，不提前宣称达到某个延迟指标。

**代码依据：** [logistics_knowledge.py](../backend/logistics_knowledge.py)，`refresh_index()`、`read()` 与 `listing()`（约第 35、52、137 行）；[logistics_runs.py](../backend/logistics_runs.py)，`authorize()`（约第 106 行）。

### 2.6 “报告完整”和“知识可靠”还没有分开表达

**问题：** 当前主要区分完整报告、部分结果，以及确定性成果、模型成果。缺少针对结论的“人工核验”“待核验”“已被后续证据修正”等状态。

**影响：** 用户容易把“完整报告”理解为“结论已经确认”。当前完整状态主要表达调查成果的完整程度，并不能单独证明结论已经经过人工核验。

**性质：** 知识治理能力扩展。用户误解的实际频率尚未验证；首版可先明确状态文案，再决定是否需要核验流程。

**建议：** 分别展示成果完整程度和结论核验状态。后续调查产生修正时，建立明确关联，保留原报告及原证据，说明修正依据与适用时点。

如实施人工核验，需先定义以下规则：

- **核验对象：** 指定报告版本中的具体结论，记录其适用区域、参考时点、指标口径和来源；不能默认把整份报告一次标为全部已核验。
- **核验人：** 由后端校验当前核验权限与数据范围，保存真实账号和核验时间；不能仅凭前端标记，也不能将已有方案审批权自动等同于结论核验权。
- **核验依据：** 保存核验结论、理由与当前授权的证据引用，区分程序复算、原证据检查和外部人工陈述；无核验依据的人工陈述继续标为未验证。
- **核验失效与修正：** 核验绑定具体版本或指纹；结论变更后不能继承旧核验状态。后续修正保留原结论，并关联修正内容、证据、核验人及适用时点。

批准某个处理方案不能直接等同于报告所有结论已核验；确认数量计算也不能等同于确认现场原因。

**验收条件：** 完整度与核验状态分别展示；未核验结论不因方案获批变为已核验；无核验权限或证据不可访问时不能提交核验；内容版本变化不沿用旧状态；修正记录可以追溯到原结论与依据。

**代码依据：** [logistics_knowledge.py](../backend/logistics_knowledge.py)，`refresh_index()` 的完整度规则（约第 35 行）；[KnowledgeDetail.tsx](../src/logistics/KnowledgeDetail.tsx)，成果状态与处理结果展示（约第 32 行）。上述核验规则为建议，不是现有能力。

### 2.7 失效引用可能让整个会话受限，缺少恢复入口

**问题：** `authorize_context()` 逐份读取会话中的成果引用。任一引用撤权、成果不存在或内容校验失败时，会话 `read()` 会返回 `restricted=true` 并隐藏上下文；携带该引用的历史消息也会被屏蔽。当前没有移除引用的接口与界面，无法通过现有引用管理操作恢复。

**影响：** 原本仍有权限讨论的其他内容可能因一份失效引用而暂不可继续使用。屏蔽受限数据是必要行为，需要补齐的是安全恢复路径。

**性质：** 已确认的会话恢复缺口。撤权导致会话和消息受限已有测试覆盖；内容校验失败的影响根据相同异常处理路径确认，尚未单独运行会话复现。

**建议：** 允许当前有效且有会话使用权限的本人移除失效引用。移除前核对会话归属、版本与处理中状态，不要求先成功读取已经失效的成果；提交后再核对剩余引用和当前调查范围。不能因为移除一份引用而解除其他撤权范围，不能修改或删除原报告。

历史消息保留其原引用信息和审计关系，继续执行权限与一致性屏蔽。删除当前上下文引用不能自动恢复显示先前已包含受限内容的消息，也不能把受限内容通过恢复通知、标题或异常原因重新暴露。

**验收条件：** 移除唯一失效引用后，剩余上下文仍合法的会话可以继续；仍存在失效引用或当前调查撤权时保持受限；历史受限消息不恢复展示；非本人、版本冲突及处理中请求按规则拒绝；重复移除幂等，且不触发调查或工具执行。

**代码依据：** [logistics_chat.py](../backend/logistics_chat.py)，`authorize_context()`、`read()`、`message()`（约第 118、145、233 行）；[test_logistics_page_integration.py](../backend/test_logistics_page_integration.py)，`test_reference_is_persistent_explainable_idempotent_and_revocable()`。

## 3. 建议实施顺序

| 顺序 | 改进内容 | 性质与实施边界 | 验收依据 |
| --- | --- | --- | --- |
| 1 | 列表故障隔离 | 已复现缺陷；保留详情与引用校验 | 2.1 节 |
| 2 | 失效引用移除与会话恢复 | 恢复缺口；历史受限内容继续屏蔽 | 2.7 节 |
| 3 | 引用管理与引用到当前对话 | 能力扩展；复用后端现有引用接口 | 2.3、2.4 节 |
| 4 | 全文关键词搜索与命中摘要 | 能力扩展；先明确字段与摘要一致性规则 | 2.2、2.5 节 |
| 5 | 按问题选择内容与证据 | 能力扩展；先解决指定任务明细及上下文边界 | 2.4 节 |
| 6 | 聊天内历史成果检索 | 能力扩展；依赖可用搜索与引用管理 | 2.2、2.3 节 |
| 7 | 核验状态与修正关联 | 可选治理扩展；先确定核验权限、对象和依据 | 2.6 节 |

性能基线可在初期采集。索引增量更新和数据库筛选分页按 2.5 节单独验证；只有测量表明确有瓶颈时才实施，必要时提前处理，不固定排在所有新功能之后。性能优化与全文搜索若共享摘要索引，应合并设计一致性规则，避免重复建设。

以上顺序是建议，不构成自动实施授权。每项按对应验收条件单独确认完成，不将界面可点击或离线通过等同于真实模型质量已验证。

如果后续希望进一步沉淀经验，可以增加经过核验的结论、适用条件和处理方法，并与原始调查报告建立明确关联。

## 4. 改进时需要保留的现有约束

- 列表、详情、下载、引用和模型上下文组装均需复核当前权限。
- 历史成果保留原区域、快照、数据批次和参考时点，不能直接作为当前事实。
- 阅读、引用和解释历史成果不自动发起新调查。
- 内容指纹、证据归属和报告一致性校验继续保留。
- 完整与部分成果继续明确区分，保留停止原因、限制和未解决事项。
- 摘要索引绑定原报告版本或指纹；原内容变化或异常后，不能继续展示旧摘要或自动刷新指纹以掩盖异常。
- 引用移除只改变后续上下文，历史消息、原报告及其审计关系保留；受限历史内容继续屏蔽。
- 搜索结果、摘要、下载、模型上下文和计数均受当前权限约束；范围筛选不代替成果整体授权。

## 5. 可执行的隔离复现
