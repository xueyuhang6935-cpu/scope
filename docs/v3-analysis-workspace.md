# V3 数据基础、分析工具与连续追问

本阶段把 V3 的确定性数据分析路径接入 Scope，包括查询、日趋势、渠道/设备分组、等长两期比较、汇总报告和受限自然语言追问。页面仍在左侧“订单与支付分析”。完整动态 Agent 调查与模型运行时仍是后续阶段。

## 使用路径

1. 启动 Scope（`npm run dev`，或构建后 `npm start`），登录并进入“订单与支付分析”。
2. 选择“14天订单与支付演示”。默认目标范围是2026-09-23至29日。
3. 直接执行趋势分析，或输入“9月23日至29日支付率趋势”。
4. 输入“只看活动渠道，再按设备拆分”。检查实际生效范围显示 channel=campaign、device分组。
5. 输入“不限渠道，比较所有设备”。渠道过滤应清除；这是设备分组，不会自动创建日期基准。
6. 输入“比较9月29日和28日订单与支付表现”。首个日期为目标，第二个为基准。
7. 导出报告包，包含 Markdown、独立SVG图表和JSON证据。网页另支持PNG下载。单独Markdown中的相对图片需要配套图表目录，推荐下载ZIP。

自然语言为 `conservative_rules_v1` 受限规则解析器，不调用大模型、不消耗模型Token。未理解的额外条件不会被静默忽略，返回澄清并保持已接受计划。“GMV”“60分钟支付率”“实时”“为什么下降”等返回不支持。输入框继承会话已接受范围，而非尚未执行的表单草稿；两者在页面分别标注。

相对日期固定使用本轮服务端 request_time，按 UTC+8 上海自然日展开。“最近7天”为已结束的7天；不会根据演示快照水位改成历史日期。多日范围追问“和前一天比较”会澄清。日期也可通过表单明确指定。

## 八个工具

`analysis_tools.ToolExecutor` 将已验证计划注入工具。先执行 `get_metric_definitions` 和 `check_data_readiness`，随后按任务走固定短路径。

| 工具 | 本阶段实现 |
| --- | --- |
| get_metric_definitions | 指标版本、定义与依赖 |
| check_data_readiness | 按指标、区间或每日检查质量和水位 |
| query_metrics | 单区间查询、受控渠道/设备交叉过滤 |
| compare_metric | 等长不重叠两期；单数差/百分点差/相对变化 |
| breakdown_metric | 单期或双期完整维度骨架、分母、权重、小样本、可用时的组内/构成分解 |
| trend_metrics | 完整日期骨架、逐日状态、全期加权总计；缺失不补零 |
| inspect_payment_errors | 同订单队列30分钟内错误尝试、受影响订单、未支付覆盖及无尝试/pending/缺码计数 |
| sample_order_timelines | 同队列窗口内样例；固定SHA-256层内排序、分层轮转、总计最多10单 |

后两个工具可通过Python独立调用，尚未作为动态调查能力开放到网页。不得将其存在等同于完整调查策略已实现。

工具只能缩小根过滤、使用已批准指标子集。业务库只读；固定SQL模板和参数绑定，无任意SQL入口。任务最多12次请求、16次执行、180秒；SQL通过SQLite progress handler实施5秒取消，缓存仍计请求次数。Python启动桥限制4个并发、180秒子进程和8MB输出。当前是小规模本地单进程原型。

图表由程序从当前证据生成：验证scope_id、输入证据哈希、指标单位、日期排序和比率范围。趋势缺失点断开，柱图从零起，比率轴0—100%，表格保留分母和小样本。默认绘制已选支付率，若没选支付率则绘制第一项指标；其余指标完整列在表格中。汇总最多3张图。完整结果持久化，模型预览字段最多50行并标注截断；当前没有模型消费这些字段。

## 会话、持久化与接口

独立应用库默认为 `Scope/data/analysis.sqlite`，可用 `ANALYST_DB_PATH` 配置。登录用户ID决定会话所有权，不能从请求体伪造。业务快照与认证数据库不承载分析写入。

- `GET /api/analyst/workspace`：新能力与快照目录。
- `POST/GET /api/analyst/sessions`：创建会话/列出自己的最近20个会话。
- `GET /api/analyst/sessions/:id`：当前已接受计划、待澄清候选和任务目录。
- `POST /api/analyst/analyze`：表单计划。
- `POST /api/analyst/message`：文本问题。
- `GET /api/analyst/sessions/:id/tasks/:taskId`：已保存结果回放，不查业务库、不改变当前焦点。

写请求包含 session_id、expected_version、client_request_id 和 payload。应用库事务内同时保存任务结果（含工具证据/报告）、新会话版本及已接受计划；重复请求ID返回已存结果，改变同ID内容则拒绝；版本冲突返回409。每会话最多10个已接受执行轮，澄清不计执行轮。新任务保存parent_task_id和plan_version。

这实现已完成任务的持久化、回看和提交后幂等，不是V3检查点中断续跑：提交前崩溃可能重做只读查询；未完成尝试日志、恢复预算、模型多调用/重试/Token计量等尚未实现。没有分布式任务调度。
