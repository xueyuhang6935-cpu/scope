## 实际行为与代码

1. `backend/logistics_model.py:report_reservation` 改为预留一次报告：同一报告输入估算 + 1200 Token 最小输出 + 512 缓冲，模型调用预留由 2 次改为 1 次。`project/agents/logistics_model.py:generate` 保留 2400 输出上限，按实际余量收缩输出；首次失败后重新检查 Token、调用次数、时间与用量可信性，报告最多修复一次。1200 是紧预算下的最小输出额度，不保证外部模型一定成功。
2. `project/agents/logistics_model.py:report_context/build_messages` 共用于预留估算与真实发送。当前三个支持目标仅携带相关逾期汇总、人员负荷、窗口/归属绑定及源限制，删除重复计划、步骤状态、观察和目标外质量明细。完整证据仍保存并用于授权及严格校验；未知目标保留原上下文路径，不引入 T14 ContextBuilder。
3. `project/agents/logistics_coverage.py:goal_followup` 只提出同查询连续页的下一页，核对范围、已保存分页参数及缺口数量；`backend/logistics_workflow.py:select/followup_fits` 在预算收尾时允许一次确定性补页或必要负荷补查。执行仍通过原参数校验、实时授权、领取凭证及家族预算；补查估算包括新增报告输入。补查失败不循环，检查点恢复保留尝试轨迹。正常流程原有并列人员负荷处理继续适用。
4. `project/agents/logistics_protocol.py:bound_limitation/source_limitations` 为新生成的绑定数字、集中程度、归属、窗口及负荷生成限制文字。完整归属明确限于当前快照；部分归属明确缺口；GPS 字段部分缺失与整个工具没有结果分开。推断、人工陈述和未绑定观察仍严格校验，历史报告读取不重新渲染。模型原始提议及规范化结果继续留存。
5. 补页失败回归发现固定模板会选中最后一个失败结果，现改用此前可用的基础证据；失败仍保存，不把失败页当作成功或完整覆盖。

输出协议保留原状态、未解问题、真实引用和绑定校验。宿主补取与人员参数绑定继续标记来源，不能算作模型自主重规划。
