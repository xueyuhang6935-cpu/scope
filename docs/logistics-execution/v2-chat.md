# 物流智能助手连续对话实现

智能助手仍使用 `/assistant`，会话地址为 `/assistant/{conversation_id}`。本次实现聊天入口、调查后的追问、持续上下文、草稿修改和独立提交；正式 T13 与 G3 状态不因此改变。

## 页面与业务流程

1. 输入调查问题，通过文字或分析范围面板确定区域与完整参考日期时点。没有日期时先澄清，2000 仅为参考年。
2. 默认创建确定性调查；面板明确选择后才使用实验模型调查。消息先保存，后台处理不依赖浏览器。
3. 结果显示程序计算指标、任务证据、完整报告和下载入口。调查结束后仍可解释已有内容。
4. 默认聚焦报告前两条任务，也可勾选具体任务；历史报告通过“讨论这份报告”重新聚焦，后端检查其属于本会话。
5. 人工事实保持未经验证，发生时间未给出时保持未知；接收时间另外保存。事实发生时间使用参考时间轴，不能据此推定历史原因。
6. 约束仅适用当前调查范围；换区域或时点不会自动继承。运行中的模型调查复用现有约束版本入口；停止后不会自动恢复。
7. 草稿使用窗口核查或联系快递员核查两类受控行动，保存具体任务与顺序。明确禁止联系快递员的短命令由程序识别，模型不能反转该限制。
8. 草稿通过聊天反复修改，不进入审批列表。明确提交命令或草稿提交按钮才提交具体版本及摘要。
9. 审核在原审批中心、运行详情完成，实际决定回到原聊天。驳回后修改新草稿；批准不等于执行。内部单、回执、复核继续使用运行详情的已有入口。

## 接口契约

接口统一在 `/api/logistics/`，沿用认证、区域授权和来源校验。

| 方法与路径 | 内容 |
| --- | --- |
| `POST /conversations` | 空对象创建自己的会话 |
| `GET /conversations?page=1` | 当前账号会话，每页20条 |
| `GET /conversations/{id}` | 上下文、当前版本、范围是否受限 |
| `GET /conversations/{id}/messages?after=0` | 顺序消息，每次最多100条；返回游标与是否还有后续页 |
| `POST /conversations/{id}/messages` | 保存消息并返回202；后台解释或分发业务动作 |

发送示例：

```json
{
  "text": "调查区域5的揽收风险",
  "request_id": "客户端生成并在重试时保持的编号",
  "context_version": 0,
  "selection": {
    "region_ids": ["5"],
    "business_as_of": "2000-07-02 10:00:00",
    "mode": "deterministic"
  }
}
```

`selection` 还允许当前报告的有序 `task_ids`，以及本会话已关联的 `run_id`，用于显式聚焦历史报告。模型不能自行指定运行、快照、权限或预算。明确提交按钮携带 `command={action:"submit",draft_version,draft_hash}`；自然语言提交也必须是明确命令，引用、否定、条件与询问不能触发提交。

同一请求编号返回原消息；换内容会冲突。发送端保留原请求内容用于重试。上下文版本冲突时，用户可核对当前对象后重新发送。模型请求结果未知不自动重发；模型错误不自动换供应商模式。

聊天协议包含动作、候选参数、回复文字和证据引用。后端检查范围、实时权限、对象归属、版本与证据。业务写入之后才生成成功说明。明确到分钟的完整日期补零秒；“区域5”规范化为编号“5”，仍需现有区域白名单及授权校验。

## 保存与恢复

使用既有业务 SQLite，初始化时兼容增加：

- `logistics_conversations`：账号、上下文、版本和时间。
- `logistics_messages`：文本、顺序、请求标识、范围、实际结果与处理状态。
- `logistics_chat_operations`：执行阶段、模型动作、固定业务参数、用量、提示词版本和受限失败诊断。
- `logistics_conversation_runs`：消息、调查、快照关联与结果/事件读取位置。
- `logistics_collaboration_operations`：业务写入的持久化幂等结果。

现有协同记录增加可选 `drafts`，旧记录读取时兼容为空。新草稿有独立版本与内容摘要；正式提交继续进入现有 `proposals`，审核对象保持一致。审核人只能读取必要方案与证据，不能通过运行详情读取私人草稿或私人会话。

快照创建和运行中约束新增仅宿主使用的操作标识，恢复时复用同一操作。现有 HTTP 快照与约束接口不因此开放额外参数。

同一应用进程中使用一个聊天执行线程及心跳，队列保存在数据库。领取凭证和租约控制提交。模型调用不持有数据库事务。重启后继续处理尚未执行消息；已经发出的未知模型请求保存中断状态；业务动作已经完成时按原操作编号读取结果。关闭服务先停聊天线程，再停调查线程和关闭检查点、数据库。

本轮引用对象在消息接收时固定。迟到调查结果关联原消息，不覆盖另一份正在讨论的报告；写入动作遇到上下文变化会拒绝。撤权后，历史文本、摘要、卡片和证据引用重新核对权限，无权内容隐藏。

迁移只增加业务表、兼容字段和协同记录字段，保留既有源记录、调查和审批。更新后重启后端加载代码；首次启动执行兼容初始化。上线前按现有数据库备份方式保留业务库与检查点一致性备份，回退时保留新增记录，不以重建库代替迁移。

## 预算与限制

- 对话与调查分别记账。聊天每次一个模型请求，无自动修复或网络重试，最多1800输出 Token，单轮输入估算加输出不超过16000 Token；实际已知用量超限阻止交付。
- 按北京时间自然日及账号累计：最多200次聊天调用、300000 Token。新建会话不能重置当天额度。未知用量保留未知标记并按已预留估算占额；实际供应商用量仍可能超过预估，不能视为账单硬限额。
- 解释保存结果不消耗原调查家族额度。补充取证必须明确选择实验模型，并继承原调查家族、实时权限和停止规则；未知调用、无进展等停止情形不自动恢复。
- 无模型配置或模型失败时保存实际失败。已有结果可直接阅读下载，不伪造模型完成。
- 最近8条消息、当前草稿、最近提交版本及按需证据进入模型；权威事实、持续约束、反证和驳回理由仍在业务记录中。上下文超过限额会明确停止，不能静默丢掉约束。
- 模型解释有来源标记；指标和任务卡片使用程序保存数据。结构和引用合法不等于自然语言结论已被证明，真实语义质量需单独审核。
- 两类行动只用于内部核查，尚未接通的执行动作不能生成虚假执行结果。批准后的变更要求新的调查与方案。
- 保持单应用进程，不新增框架或依赖；会话状态逐项轮询，较大规模时需要改用持久化事件游标。

## 验证入口

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest backend.test_logistics_chat -v
npx playwright test tests/logistics-chat.spec.ts tests/frontend-restoration.spec.ts
.\.venv\Scripts\python.exe -X utf8 scripts/verify-logistics-chat.py --live --output test-results/logistics-chat/live.json
```

真实验证脚本只读源库，业务账号、会话、草稿与提交写隔离 SQLite。脚本保存各轮动作、状态、实际回复、用量、独立复算差异、限制是否生效、任务顺序及源摘要前后检查。开发失败产物保留；真实对话检查不能替代 T13 规划增量评价或正式阶段验收。
