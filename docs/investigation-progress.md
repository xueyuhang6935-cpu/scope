# 调查进度与停止逻辑（runtime v2）

运行时阶段为 investigating → finalizing → finished。原预算保持：工具请求12、实际执行16、模型请求10、任务Token20000、会话Token100000、执行180秒。解析请求与Token计入同任务模型额度。

工具耗尽后停止数据调用；剩余模型、Token与时间足够时，只开放 finish_investigation。最终提交是控制动作，单独计 control_requests，不占数据工具额度。收尾最多两次模型请求（含限流重试和修正），并受原总预算约束。超出工具预算的已接收批量请求仍逐一回传拒绝结果，观测请求数可超过上限，但不执行额外查询。

收尾使用去重后的证据与当前进度，完整工具响应仍在审计记录。Token预留包含消息、工具Schema和输出额度；这是估计，不是服务商账单硬上限。

`query_stop_reasons` 记录停止查询的触发项；`stop_details` 记录整个任务结束原因。后者可为正常完成、证据不足、时限、模型次数、任务/会话Token预留不足、未知用量、模型错误等。结构中保存触发时用量、上限及预留额度。旧历史报告不会被改写成新诊断。

检查点 `investigation` 保存：

- checked_scopes：仅已提交工具结果的范围、日期、状态与证据引用；执行成功不等于数据可用。
- requirements：整体指标比较、用户指定分组、显式必需检查与定位依据的逐项状态。
- next_checks：未完成必需项与模型提出的可选问题，二者明确区分。
- candidate_explanations：登记类型的候选解释、支持/可能反证引用、待补证据。文本由模板生成；标记待核实，不证明原因。
- rejected_updates：被范围/引用检查拒绝的进度更新。

计划新增可选 `required_checks`：payment_errors、order_samples。模型解析器只有在用户原话明确要求时才允许加入；根范围检查不能用缩小后的子群检查替代。旧计划省略该字段时保持原义。普通表单未新增检查开关，可通过聊天指定。

候选解释与反证引用必须属于本任务、来自已完成证据，并匹配声明范围；渠道证据不能支持设备子群声明。构成解释还需同范围可用分解。语义关系依然需要人工核对。可选问题由模型在 progress 中提交，没有提交就明确显示为空，不自动捏造解释。

completed 要求必需清单全部交付、具有完整分组定位证据且最终提交通过核验。预算导致遗漏保留 budget_exhausted；证据不足不冒充完成。工具耗尽但必要工作已完成，仍可完成收尾并返回 completed。

恢复保持原截止时间与预算，并保留阶段、候选解释和完成清单。修复了 JSON 回载后 pending/calls 不再共享引用的问题。已有完成结果原样回放；匹配旧 v1 签名的未完成检查点可显式升级到 v2，不清空用量和证据；其他版本/快照/模型变化仍拒绝恢复。
