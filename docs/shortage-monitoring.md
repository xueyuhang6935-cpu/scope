# 缺料计算与自动风险监测

## 已交付能力

应用直接读取现有 PostgreSQL `supply_demo` 场景的 BOM、生产计划、库存、占用、冻结、采购承诺和物流记录，执行确定性缺料计算。运行结果、事件、变更历史和交期注入保存在独立的 `sc` 区域，原始场景不被修改。不读取 `expected_results`、预置风险、方案、审批或关闭记录作为计算答案。

工作台和风险列表已使用后端实际计算结果；旧 `EVT-*` 页面仍为带标记的设计样例。审批与业务执行不在本次交付范围。

## 使用

1. 保持本地 PostgreSQL 运行，服务端 `.env` 配置已有 `ANALYST_DATABASE_URL`。该账号需要读取 `supply_demo`，并创建/读写 `sc`。无需模型密钥。
2. `npm run dev` 启动前后端。在“数据中心 → 数据接入 → 配置数据库”选择 `supplier_delay` 并“保存并接入”。
3. 进入工作台，点击“立即扫描”，或等待默认每 60 秒的自动扫描。A 厂 P001 首次缺料为北京时间 2026-10-07 16:00，最大缺口 400 件。
4. 打开风险详情，查看结余曲线、需求时间线、受影响计划、来源证据；可以分配负责人、确认风险，并保留变更历史。
5. 展开“监测设置与交期变更”，将 `PO-FOCUS`、批次 `01` 的到线承诺改为 `2026-10-06 08:00`，缺口消失，事件进入“当前窗口已覆盖”。改回 `2026-10-08 08:00`，生成与原事件关联的复发事件。输入时间均为北京时间。
6. 在智能助手询问“检查 P001 未来三天缺料风险”，核对场景、工厂、物料和已知证据截止时间后确认，得到同一计算服务的结果。每条历史回答保存当次证据，不随后续注入改写。

未接入数据库时，文件导入的库存/质量查询继续可用，缺料问题仅返回就绪检查。数据库已接入但故障时不会降级成示例结论。

## 计算口径

- 合成场景有明确期初和两周窗口。`days` 为从场景起点开始的 1–14 个自然日；`asOf` 是获知证据截止时间，不是需求窗口起点。初始使用场景的 `initial_as_of`，不会跟随计算机时钟跨到未来。推进回放需显式保存新的时点。
- 在一次 PostgreSQL 可重复读事务内读取快照，按 `ingested_at` 筛选；承诺还检查 `known_at` 和 `changed_at`。完整输入生成 SHA-256 快照摘要，结果记录算法版本。
- 生产计划按业务行选择当时有效的最新版本，再按需求时间选择唯一有效且已批准的一层 BOM 和适用物料修订版。换算规则必须唯一有效。缺少库存记录、BOM、物料修订版、换算规则或未确认数据完整性时输出不可计算，不以零代替。
- 期初库存必须对应场景起点。不同修订版不互相替代；冻结库存不可用。计入生产需求的占用不重复扣减，外部占用扣减；解冻/释放仅在已知且到达业务时间时回补。库存与冻结、占用重叠口径不明时不能计算。
- 同一采购行同一批次只使用最新承诺。采购未交与在途不是两份供给；收货数量与采购已交数量以同一口径核销。无显式批次关联时，按承诺时点和发运 ETA 顺序分配收货/发运数量。部分在途仅改变对应数量的供给时点。
- `supplier_commitments.available_at` 表示承诺到线时间；发运 ETA 加收货、检验和配送时长后若更晚，则推迟相应在途数量的可用时间。过期且没有到线证据或新承诺的供给标为数据不足。
- 实际新增供给必须关联收货、质量放行和实际到线，且不能再次计入期初已有批次。已知实际跨厂发运会扣减调出厂库存；来源记录缺失时，不能推断调出厂仍有完整库存。
- 同一时刻先处理供给，再处理需求；生产需求按时点、计划号、行号分配。单物料输出期初、各时点结余、最大缺口、首次缺料、短缺窗口和受影响计划。安全库存告警与负库存短缺分开。同一生产计划的多物料影响取最大受影响车辆数，避免重复相加。

这是固定场景的供需测算，不是实时 ERP 库存、复杂排产或业务执行引擎。

## 监测与事件规则

- 后端生命周期内运行一个独立于 HTTP 请求的监测线程，每 5 秒检查已接入账号的到期配置，按配置间隔扫描（10–3600 秒）。配置、上次检查时间、错误状态持久化在应用 SQLite，重启后继续检查到期任务。`SUPPLY_MONITOR_AUTOSTART=0` 可禁用自动线程；测试环境默认禁用。
- 数据库配置保存唤醒监测器；交期注入提交后立即扫描；外部源数据变化在下一次到期扫描中识别。只有在回放时点前已获知的数据会影响结果。
- 同一账号场景、工厂、物料、修订版的持续短缺合并为一个事件，事件内保存全部短缺窗口。时间移动或证据变化会更新版本，不每次建单。完全相同的计算结果复用扫描记录。
- 事件状态为待处理、已确认风险、待补充数据、当前窗口已覆盖。数据不完整或原需求退出窗口时不能将旧风险自动标为已覆盖。
- 已覆盖后再次出现缺口会创建关联前次事件的复发记录。“已覆盖”仅表示该计算窗口不存在缺口，**不等于已收货核验、已执行处置或正式关闭**。
- 每次扫描用 PostgreSQL 事务级 advisory lock 与部分唯一索引防重复；事件编辑使用版本校验。重复交期注入请求复用同一请求编号，内容冲突返回 409。扫描失败保留上次成功结果，下一周期重试；提交后扫描失败可用相同请求编号重试注入。
- 当前为账号隔离的模拟工作空间，每个账号/场景有持久 UUID，避免不同本地账号库共用数据库时串号。工厂筛选由后端执行；企业共享工厂权限、审批角色仍属后续能力。
- 仍采用单 Uvicorn 应用进程。该监测线程不等同于审批/业务执行的持久任务队列，后续执行 worker、租约和审批恢复另行实现。

## 接口

接口均要求登录；写请求复用供应链接口来源校验。错误不返回原始数据库连接字符串或驱动详情。

| 接口 | 用途 |
| --- | --- |
| `GET /api/supply/monitor` | 当前账号选中场景的监测配置；未配置返回 `configured:false` |
| `POST /api/supply/monitor` | 设置 `asOf`、`days`、`enabled`、`intervalSeconds` |
| `POST /api/supply/shortage` | 只计算，参数 `factory`、`material`、`days`、`asOf`；不创建事件 |
| `POST /api/supply/monitor/scan` | 计算并事务更新风险事件 |
| `POST /api/supply/monitor/commitment` | 注入 `purchaseLineId`、`installment`、`availableAt`、`requestId`，可选 `knownAt`、`note` |
| `GET /api/supply/risks?factory=A` | 当前场景的事件和最近一次成功计算 |
| `GET /api/supply/risks/{id}?factory=A` | 事件详情、当次证据和版本历史 |
| `POST /api/supply/risks/{id}` | 带 `version` 更新 `owner`，或在 `open`/`acknowledged` 间切换 |

`backend/risk_schema.sql` 为首版迁移，首次使用自动执行并记录 `sc.schema_versions`。历史查询结果包含精确十进制字符串；前端按物料分别显示，不能跨单位加总。

## 验证

```powershell
$env:SCOPE_DATABASE_INTEGRATION='1'
.venv/Scripts/python.exe -X utf8 -m unittest backend.test_shortage backend.test_supply backend.test_database_connection -v
npm run lint
npm run build
npx playwright test tests/supply-live.spec.ts tests/supply.spec.ts tests/assistant.spec.ts --reporter=line
```

计算测试对照 12 个固定场景的独立预设答案，并检查时间边界、部分在途、有效 BOM、占用、冻结、未来记录隔离和车辆去重。生命周期测试覆盖合并、重复扫描、并发、交期注入幂等、复发、账号隔离、版本冲突、重启和证据持久化。测试使用独立账号工作空间，结束时仅清理这些空间的 `sc` 运行记录，不修改 `supply_demo`。
