## 1. 升级目标

用户在智能助手中提出调查问题，Agent 根据当前授权范围和业务时点执行调查，在原对话中返回结论、重点任务、证据、报告下载和后续建议。用户可以继续追问、补充事实、调整约束、讨论方案，直到形成可提交版本。明确提交后，方案进入审批中心；审核结果返回原对话，支持根据驳回原因修改并重新提交。

第二版的核心验收要求是：用户从聊天发起调查，持续追问并完善方案，提交后在审批中心看到同一版本；驳回后能够回到原聊天继续修改。用户无需先到工作台逐项填写表单才能完成上述过程。

### 1.1 页面职责

| 页面 | 第二版职责 |
| --- | --- |
| 智能助手 | 主操作入口：调查、澄清、结果阅读、连续追问、事实补充、约束修改、方案讨论、提交与后续跟进 |
| 工作台 | 展示风险概览和回放指标，保留直接启动调查入口，并允许关联至对话 |
| 运行详情 | 查看调查阶段、工具调用、原始证据、预算、错误与恢复情况 |
| 审批中心 | 核对已提交方案的内容、版本与证据，记录批准或驳回 |
| 数据管理 | 管理批次与授权范围内的历史源数据，不作为未经掩码的模型输入 |

### 1.2 与现有实施任务的关系

- T13 继续暂缓，保留真实对照结果和失败记录，G3 保持未通过。
- 第二版补齐聊天所需的意图识别、上下文管理和指代解析，不将这些能力继续留作不可用占位。
- 第二版中的上下文和协同能力与 T14—T20 有交集；完成第二版局部功能不自动代表对应正式任务或 G4—G6 全部验收通过。
- 模型负责理解问题、选择受支持的步骤和组织回复；数量、时点、证据、权限、预算、方案版本和审批状态由程序核对。

## 3. 用户体验与目标业务流程

### 3.1 连续对话示例

| 用户操作或业务事件 | Agent 的预期响应 | 必须保留的业务关联 |
| --- | --- | --- |
| “调查区域5在10:00的揽收风险” | 结合已选日期和时点判断范围；条件不足时澄清，充分时创建快照并启动调查 | 区域、完整参考时点、快照、调查运行 |
| 调查执行中 | 展示真实进度，例如正在创建快照、核查逾期任务、整理报告 | 当前消息与后台运行 |
| 调查完成 | 给出结论、重点任务、依据、未解问题和报告下载 | 报告、证据、重点任务编号 |
| “这两条为什么逾期？” | 解析当前两条任务，读取已有证据；原因未证实时说明缺口，必要时继续取证 | 当前聚焦任务及其调查范围 |
| “现场反馈有人手不足” | 保存人工陈述，注明来源、时间和未经验证状态 | 人工陈述与所关联任务 |
| “先核查窗口，暂时不要联系快递员” | 保存分析约束，调整后续调查或建议 | 约束版本与适用范围 |
| “按这个方向生成一个方案” | 形成结构化方案草稿，列出行动、对象、依据和待确认事项 | 草稿、引用证据与当前约束 |
| “先处理第二条，再完善说明” | 修改指定草稿，说明变更 | 任务指代、草稿版本与修改记录 |
| “把这个方案提交审批” | 校验当前草稿，提交指定版本，返回待审核状态及入口 | 提交版本、内容摘要、审批对象 |
| 审核人驳回 | 原聊天显示驳回理由，支持继续讨论和生成新草稿 | 原审核决定、驳回原因、后续版本 |
| 审核人批准 | 原聊天显示批准状态，说明尚未执行，引导内部跟进 | 批准版本与后续内部单 |
| 记录回执并推进时点 | 保存真实/模拟标记，创建新快照，分别复核旧风险与新流入 | 回执、新快照、复核结果 |

“10:00”只有在对话已经确定参考日期时才足以执行；缺少日期、区域或出现范围冲突时，助手需要澄清。

### 3.2 对话中的对象指代

- “这两条”：通常对应最近展示或用户明确选择的两条任务，必须有具体任务编号。
- “刚才的报告”：对应当前讨论的报告，同时保留其快照与时点。
- “这个方案”：对应当前聚焦的草稿或已提交版本，不能只通过一段标题判断。
- “按刚才的约束”：读取持续生效的约束记录，不能仅依赖模型记忆。
- “按审核意见修改”：读取实际保存的审核决定和驳回原因。

存在多个合理候选对象时，助手应在聊天中澄清，不直接执行含糊的提交或修改。

## 4. 六项核心改造

### 4.1 接通真正的物流聊天会话

#### 页面行为

- 保留现有聊天布局、编辑器和导航。
- 提供新建对话、历史列表、打开历史会话、用户消息与助手回复。
- 发送成功后显示已保存的消息；处理过程有可理解的进度。
- 发送失败保留草稿或原消息，显示实际失败状态与可行的下一步。
- 刷新、关闭页面或重新登录后，可以恢复消息、调查关联和当前业务状态。

#### 后端职责

会话需要关联创建者、当前授权范围、消息、调查、快照、报告与方案。消息先保存，再执行或调度业务动作；后台调查继续复用现有持久化运行机制，不依赖浏览器页面存活。

一个会话可关联多次调查；每次调查保留独立范围和证据。会话的当前聚焦对象与历史关联分别保存。

账号切换后重新读取权限。审核人可以读取获授权方案及其必要证据，不自动获得发起人的全部私人对话。

#### 完成标准

消息可发送、有实际回复、有历史记录；关页后后台调查继续，重开后能恢复结果；不同账号的对话和数据权限得到正确隔离。

### 4.2 让聊天消息驱动业务流程

新增自然语言与现有物流服务之间的对话处理能力，按当前问题及业务状态识别受支持的动作。

| 动作 | 处理要求 |
| --- | --- |
| 发起调查 | 确定区域、完整时点和数据批次，创建已授权快照，启动调查 |
| 解释结果 | 读取当前报告和证据，解释数量、排序、任务状态和已知限制 |
| 继续取证 | 判断缺口，创建受控后续调查或按合法机制继续处理，保留原关联 |
| 补充事实 | 保存人工陈述、来源、时间及未经验证标记 |
| 修改约束 | 保存结构化约束和适用对象，影响后续调查与草稿 |
| 生成或修改草稿 | 根据证据、当前约束和历史意见生成受支持的方案内容 |
| 提交审批 | 识别用户明确提交意图，校验具体草稿与版本后写入待审状态 |
| 查看审核状态 | 读取真实审批记录，解释当前状态和理由 |
| 跟进与复核 | 引导内部单、回执和新快照复核，保存独立业务状态 |

模型输出必须转为明确动作和候选参数。后端负责对象归属、字段、权限、版本与预算校验，模型不能直接写数据库或绕过工具执行。

条件充分的受支持只读操作直接推进；条件不足、范围冲突、对象有歧义或动作不受支持时，助手明确说明并澄清。

同一消息的网络重试应关联原操作，避免重复调查或重复提交。模型调用结果未知时保持未知或失败状态，不盲目重放请求。

### 4.3 补齐多轮上下文

采用“结构化业务状态＋近期对话＋按需读取证据”的方式，模型用上下文理解表达，后端保存权威业务关联。

#### 应保存的上下文

| 内容 | 用途 |
| --- | --- |
| 当前区域、参考时点、批次与快照 | 限定当轮讨论的数据范围 |
| 当前及历史调查运行 | 关联已有结果与后续取证 |
| 当前报告与重点任务 | 解析“刚才的报告”“这两条” |
| 已取得证据与未解问题 | 避免重复读取，判断结论能否成立 |
| 人工陈述与核验状态 | 区分已证实事实和用户提供的信息 |
| 人工约束及版本 | 保留调查顺序、行动限制与建议要求 |
| 当前草稿、提交版本与状态 | 解析“这个方案”并避免版本混淆 |
| 驳回原因和历史决定 | 支持按审核意见修改，避免重交原内容 |

#### 三种后续操作的区别

1. 解释已有结果：使用原报告和原证据，保留原时点，通常不创建新的计算。
2. 继续取证：在明确关联的调查范围内补充证据，受现有任务家族预算和实时权限约束。
3. 改变区域或时点：创建新的快照和调查关联，明确切换当前范围；旧报告保持原语义，供显式比较。

同一会话出现多次调查时，不能把不同快照的事实拼成一份未注明来源的结论。

#### 指代解析和上下文保留

优先结合用户明确选择的对象、最近展示的对象和当前聚焦状态解析指代。模型返回候选对象后，程序检查对象属于当前会话或允许关联的业务记录。

约束、未解问题、反证和驳回原因保留为明确记录。压缩历史消息时不能删除持续生效的约束，也不能把模型生成的摘要变成新的权威事实。

已停止的模型调查不能仅因用户发出追问而自动清零预算或无条件恢复；后续处理必须使用明确、受控的关联或恢复机制。

### 4.4 把结果整理成易读的聊天回复

回复采用“简短结论＋业务卡片”，优先说明发现、依据、限制和用户下一步能做什么。

| 展示内容 | 具体要求 |
| --- | --- |
| 结论文字 | 说明范围、时点、主要风险和当前能确定的内容 |
| 指标卡片 | 展示程序计算结果；缺失、不可计算和零值区分 |
| 重点任务卡片 | 展示任务编号、等待/逾期时长、风险状态与证据入口 |
| 证据入口 | 可以展开依据，保持与当前报告及调查的关联 |
| 报告卡片 | 展示报告名称、业务范围、状态、下载和完整阅读入口 |
| 后续建议 | 展示建议顺序、待核查事项及可用操作 |
| 进度与停止说明 | 展示真实阶段、失败原因、部分结果和未完成项 |

参考回复形式：

> 在区域5的10:00参考快照中发现2条逾期未完成任务。现有证据可以确认逾期状态，尚不能确认现场原因。建议先核对窗口与当前现场情况。
>
> 下方可查看两条任务的证据、下载报告，或继续询问具体任务。

程序计算、人工陈述和模型推断需要有清楚标记。无可用GPS不证明人员没有到场，风险集中不等于责任或因果。

调查进度通过实际后台状态更新。详细工具日志、原始计算结果和审计标识继续放在运行详情，聊天不把整段内部状态JSON作为默认回答。

模型不可用、超时或预算耗尽时，要展示实际已取得的结果和限制。若使用确定性基础结果，应明确标记其来源。

### 4.5 把建议草稿与提交审批分开

增加独立草稿阶段，使方案可以在聊天中反复讨论：

**形成草稿 → 对话修改 → 核对当前内容 → 明确提交 → 等待审核。**

#### 草稿结构

| 字段 | 内容要求 |
| --- | --- |
| 标题与目标 | 本次核查或跟进要解决什么问题 |
| 核查对象 | 明确任务编号与适用范围 |
| 具体行动 | 使用受支持的行动类型，逐步完善行动参数 |
| 优先级与顺序 | 说明先处理哪一项及其依据 |
| 负责人和时间要求 | 需要时由用户补充；不能编造现场人员或资源 |
| 依据 | 关联报告、任务证据与已有观察 |
| 人工约束 | 保留当前生效要求 |
| 待确认事项 | 明确未验证信息及提交前所需条件 |
| 预期产出 | 例如窗口核查记录或后续处理建议 |
| 版本与变更说明 | 记录本次相对前版修改的内容 |

当前固定核查策略可以作为初始受控行动，后续按实际数据与业务能力扩展。涉及系统尚未接通的执行动作时，明确标为建议或人工跟进，不生成虚假的执行结果。

#### 提交规则

- 讨论与修改阶段保存为草稿，尚未进入待审列表。
- 用户明确说“提交这个方案”或点击对应提交操作后，后台核对当前草稿、必需字段、权限和版本。
- 保存待审版本及内容摘要，聊天和审批中心引用同一业务对象。
- 已提交版本保持可追溯；后续修改生成新版本，不能改写旧版本的审核依据。
- 重复提交同一操作返回原结果，不产生多份待审方案。
- 用户自然语言“批准”不能绕过审核身份和自批门禁。

参考提交回复：

> 方案 v2 已提交，当前等待审核。可以查看提交内容或打开审批中心。

### 4.6 让审批结果回到原对话

审核人在审批中心核对方案、范围、版本、证据和约束，作出批准或驳回。决定保存后，原聊天读取并展示真实结果。

#### 驳回后的处理

- 显示被驳回的具体版本、审核人、理由和时间。
- 保留该决定与历史方案，不覆盖原内容。
- 用户说“按这个意见修改”时，读取实际驳回原因，生成新草稿并说明差异。
- 新版本重新提交，仍需独立审核；不能自动批准或无变化重交。

#### 批准后的处理

- 聊天明确显示已批准、尚未执行。
- 引导有权限的发起人创建内部跟进单，不自动冒充外部派单。
- 记录回执的操作者、来源、时间、真实/模拟标记和核验状态。
- 用户选择更晚参考时点后，以新快照复核旧风险队列与新流入任务。
- 批准、内部跟进、回执、调查完成和风险变化分别展示。

审批状态回传优先复用现有持久化事件和读取机制，重开聊天时也能读取已发生的决定，避免重复显示同一业务事件为多条新的回复。

## 5. 实现组织与复用边界

### 5.1 三层职责

| 层次 | 职责 | 复用或扩展方向 |
| --- | --- | --- |
| 聊天页面 | 输入、历史、回复、进度、卡片与业务入口 | 复用聊天布局和编辑器，新增真实物流聊天页面与卡片 |
| 对话处理与上下文 | 意图识别、参数与指代解析、当前对象、约束、动作分发 | 增加物流会话和消息持久化，按需扩展 Agent 上下文能力 |
| 物流业务服务 | 快照、指标、调查、证据、报告、方案、审核、跟进和复核 | 复用当前物流实现，重点扩展草稿与提交的业务契约 |

先定位现有组件和模块的共享契约，按实际职责增加必要文件，不为第二版另建整套认证、数据库访问或调查执行框架。

### 5.2 当前可复用模块

- 页面入口与范围权限：`src/logistics/LogisticsPages.tsx`、`LogisticsShell.tsx`、`api.ts`。

### 5.3 需要新增或扩展的契约

- 已有报告解释与必要后续取证的分发。

- 审核及跟进事件与原聊天的关联。

接口继续放在正式物流 API 范围内。本文不宣称上述新增接口已经存在。

## 6. 关键数据与状态要求

### 6.1 最小持久化内容

| 对象 | 应保存的核心内容 |
| --- | --- |
| 会话 | 所属账号、标题、状态、当前聚焦对象、历史调查关联 |
| 消息 | 角色、文本、请求标识、时间、处理状态和业务对象引用 |
| 动作记录 | 识别动作、参数、澄清情况、实际操作及结果关联 |
| 会话上下文 | 范围、时点、任务、报告、证据、未解问题、约束和版本 |
| 方案草稿 | 结构化内容、版本、证据、修改原因、待确认事项 |
| 审批关联 | 提交版本、内容摘要、实际决定及原会话引用 |

优先保存对现有业务对象的引用，避免复制出内容容易失同步的第二份报告或审批决定。

### 6.2 状态区分

- 消息状态：已保存、待澄清、处理中、已回复、部分完成、失败或取消。
- 调查状态：沿用现有运行状态，消息处理状态不能代替调查是否完成。
- 方案状态：草稿、待审核、已驳回、已批准，以及必要的失效状态。
- 跟进状态：内部单已创建、待回执、模拟回执、人工报告已执行但待核验、未执行。
- 复核状态：新快照就绪、比较完成或复核失败；不能等同真实业务已关闭。

聊天显示来自后台保存状态。方案卡片、审批列表和原聊天必须能够对齐同一版本及状态。

## 7. 数据、权限与执行边界

- 2000年仅为参考时间轴，真实年份未知；不能推断真实星期、节假日或天气。
- 模型只读取符合业务时点的已授权快照及证据，继续执行未来字段掩码。
- 用户输入的区域、时点和对象需要后端校验；模型不能扩大权限。
- 人工陈述未经验证，不能自动变成已证实事实；合成反馈和模拟回执保留明确标记。
- 发起人不能自批；当前权限、版本和内容摘要由后端核对。
- 同一快照的继续调查接受现有家族预算约束，恢复与换键不能清零已有用量。
- 模型失败、停止或用量未知时保留真实状态，已取得证据可作为部分结果展示。
- 批准不等于执行，内部单不等于外部派单；历史完成不能归因于模拟建议。
- 源记录保持不变；新增业务持久化采用兼容迁移，不通过重建库代替升级。
- 维持现有单应用进程边界，新增消息处理优先复用现有可靠调度能力。

## 8. 分阶段实施顺序

第二版按照两段业务闭环实施，各批次只在实际完成和验证后更新状态。

### 8.1 第一段：聊天发起调查、结果与报告、连续追问

| 批次 | 实施内容 | 交付与完成标准 | 当前状态 |
| --- | --- | --- | --- |
| V2-01 | 会话、消息保存与发送入口 | 用户可发送明确调查问题，关联实际后台运行，刷新后恢复消息与状态 | 待实施 |
| V2-02 | 意图、范围、指代与多轮上下文 | 支持澄清、解释、事实补充、约束修改和受控继续调查；正确解析当前对象 | 待实施 |
| V2-03 | 可读回复、证据与报告卡片 | 聊天展示结论、任务、证据、报告下载、进度、部分结果和失败说明 | 待实施 |

第一段验收：连续完成“调查 → 查看结果与报告 → 追问两条任务 → 补充约束 → 刷新继续交流”，无需跳到工作台逐项操作。

### 8.2 第二段：方案讨论、提交审批、审核结果回到聊天

| 批次 | 实施内容 | 交付与完成标准 | 当前状态 |
| --- | --- | --- | --- |
| V2-04 | 草稿、修改与独立提交 | 在聊天中完善草稿；明确提交后审批中心出现同一版本及内容 | 待实施 |
| V2-05 | 审核结果回传与后续协同 | 驳回理由回到原对话，支持修改重提；批准后引导内部单、回执和复核 | 待实施 |
| V2-06 | 连续对话、权限和恢复验收 | 验证完整用户流程、版本一致、重复请求、撤权、刷新恢复及真实模型表现 | 待实施 |

第二段验收：连续完成“讨论草稿 → 提交 → 另一账号驳回 → 原聊天修改 → 重提 → 批准 → 内部回执 → 新快照复核”。

这两段共同构成第二版完整体验。第一段完成不能替代第二段交付，聊天接口接通也不能自动证明模型质量已经达标。

## 9. 验收清单

### 9.1 主流程

1. 调查员进入智能助手，选择或通过对话确定授权区域与完整参考时点。
2. 输入调查问题，消息保存，实际快照与运行创建，聊天展示真实进度。
3. 完成后收到可读结论、重点任务、证据入口与可下载报告。
4. 追问“这两条为什么逾期”，正确关联刚展示的任务；不足以确认原因时说明限制。
5. 输入分析约束，后续回复和草稿持续遵守该约束。
6. 生成草稿并通过自然语言修改，审批中心此时尚未出现待审提交。
7. 明确提交后，聊天与审批中心读取相同方案版本和内容。
8. 审核人驳回，原聊天显示实际理由；发起人据此修改并提交新版本。
9. 审核人批准，聊天显示已批准但未执行，随后引导内部跟进与回执。
10. 使用更晚新快照复核，旧风险与新流入分别展示，保持禁止因果归因说明。

### 9.2 专项场景

| 场景 | 验收要求 |
| --- | --- |
| 缺少区域或完整日期时点 | 先澄清，不使用未声明的默认范围执行 |
| 同一会话包含两份报告 | 能解析明确指代；有歧义时澄清 |
| 改变区域或时点 | 新建快照和调查关联，旧结论与证据保持原范围 |
| 只解释已有结果 | 复用已保存证据，避免无必要的重新调查 |
| 持续约束与历史压缩 | 约束、未解问题、反证和驳回原因保持可用 |
| 重复发送或提交 | 同一操作不产生重复调查或重复待审方案 |
| 调查失败、部分结果或模型不可用 | 实际状态与限制可见，不显示虚假完成 |
| 用户关闭页面 | 后台工作独立运行，重开后恢复实际结果 |
| 权限撤回或账号切换 | 后端拒绝失效操作，前端清除无权查看的业务内容 |
| 自批或过期版本审核 | 后端拦截，历史内容与决定不被改写 |
| 草稿修改与正式提交 | 草稿、提交版本和审核对象有明确边界 |
| 驳回后修改 | 新草稿引用真实理由，旧版本及其决定保持可追溯 |
| 审核事件重复读取 | 原聊天避免重复生成相同业务事件消息 |
| 桌面与移动页面 | 对话、卡片、报告和方案操作清楚可用，无横向溢出 |

### 9.3 验证方式与证据

- 后端专项验证权限、范围、事务、幂等、版本、草稿提交和状态关联。
- 核心协议验证意图、指代候选、上下文保留、证据引用与受支持动作。
- 浏览器使用真实隔离后端完成连续对话、跨账号审核、重开和移动布局验收。
- 真实数据验证快照、指标、报告与任务关联，人工演示输入明确标记。
- 真实模型验证自然语言理解、连续追问、回复依据和失败行为，记录供应商调用、预算和实际结果。
- 离线模拟只证明流程或协议行为；真实模型语义表现与T13规划增量评价分别记录。

本文仅定义后续验收要求，没有执行或声明任何第二版测试通过。
